# cross-review

[![tests](https://github.com/troyan-dy/cross-review/actions/workflows/test.yml/badge.svg)](https://github.com/troyan-dy/cross-review/actions/workflows/test.yml)
[![license: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](./LICENSE)

> Cross-vendor code review plugin for [Claude Code](https://code.claude.com): Claude and Codex review the
> same change with the same lenses, then cross-examine each other's findings, answer objections and leave
> the disputes to a moderator. The skill talks to the user and writes its reports in Russian.

Перекрёстное ревью двумя вендорами моделей. Claude и Codex читают одно и то же изменение с одними и
теми же линзами, затем каждая сторона проверяет по коду находки другой, автор отвечает на
возражения, а оставшиеся споры разбирает модератор. Итог — список замечаний с пересчитанными
приоритетами и страница с перепиской по каждому пункту.

Плагин нужен, когда ревью одной моделью мало: перед мержем большой или рискованной ветки, когда
важно отсеять ложные срабатывания и увидеть, в чём модели расходятся.

## Установка

Репозиторий — одновременно плагин и маркетплейс Claude Code. В сессии Claude Code:

```text
/plugin marketplace add troyan-dy/cross-review
/plugin install cross-review@cross-review
```

То же из терминала:

```sh
claude plugin marketplace add troyan-dy/cross-review
claude plugin install cross-review@cross-review
```

Обновление — `claude plugin update cross-review@cross-review`: Claude Code подтягивает новую версию,
когда в [`.claude-plugin/plugin.json`](./.claude-plugin/plugin.json) меняется `version`.

## Что нужно заранее

- **Claude Code** с доступом к моделям уровня, на котором идёт ревью (по умолчанию `opus`, для
  независимых модераторов — `fable`).
- **`codex` CLI с выполненным входом** — им запускается сторона Codex:

  ```sh
  npm install -g @openai/codex
  codex login
  codex login status
  ```

  Последняя команда должна сообщить, что вход выполнен. Модели Codex из настроек по умолчанию
  (`gpt-6.1-sol`, `gpt-6-astra`) должны быть доступны вашему аккаунту — иначе задайте свои, см.
  [настройку](#настройка-под-репозиторий).

  Скил запускает `codex exec` с флагом `--ignore-user-config`: плагины, MCP-серверы и хуки из
  `~/.codex/config.toml` в прогон не попадают. Если Codex у вас работает только со своим конфигом
  (свой провайдер модели, прокси), задайте в окружении сессии `CROSS_REVIEW_CODEX_USER_CONFIG=1` —
  тогда конфиг сохранится. Иначе сторона Codex не ответит, и прогон остановится.

- **`python3` версии 3.9 или новее** — на нём работают скрипты скила, сторонние пакеты не нужны.
  Проверка — `python3 --version`. На macOS Python ставится вместе с Xcode Command Line Tools
  (`xcode-select --install`) или через `brew install python`.
- **`git`** — ревьюируемый код должен лежать в git-репозитории.
- **Необязательно: `gh` или `glab`** — чтобы ревьюировать PR GitHub или MR GitLab по ссылке или номеру.
  Без них назовите ветку и базу сами.

## Состав плагина

### Скил `cross-review`

Перекрёстное ревью ветки, диапазона коммитов, PR/MR, пакета или незакоммиченной работы: находки двух
вендоров, синтез, проверка, спор сторон и итоговый отчёт. Агент поднимает скил сам на фразы
«перекрёстное ревью», «пусть Claude и Codex проверят друг друга», «cross-review»; вызвать явно —
`/cross-review:cross-review`.

Можно назвать предмет и уровень моделей: «перекрёстное ревью ветки feature/login», «перекрёстное ревью
PR #456 лучшими моделями», «cross-review последних трёх коммитов, sonnet против gpt-6-sol».

### Скил `cross-review-setup`

Готовит в репозитории `.cross-review/` — настройки моделей, промтов и линз в состоянии по умолчанию,
чтобы владелец увидел, что можно поменять. Вызвать — `/cross-review:cross-review-setup [путь]`, или
попросить агента «настрой перекрёстное ревью». Свои файлы владельца команда не перезаписывает.

## Как устроен прогон

Прогон идёт пятью стадиями. Каждая пишет свой результат в каталог прогона, следующая читает его
оттуда.

1. **Находки.** Ростер ревьюеров запускается параллельно: по умолчанию `bugs` (линзы `bugs` и
   `impl`) и `arch` (линзы `architecture` и `quality`), каждый — одновременно на Claude и на Codex.
   Получаются четыре агента. Они только читают код и отвечают JSON по схеме. Если одна сторона
   потеряла агентов (кончилась квота, сломался ответ), спор не начинается: одна модель против
   пустоты ничего не проверяет.
2. **Синтез.** Агент Claude без доступа к коду сливает дубли, пересчитывает уверенность по числу
   источников и отсеивает замечания уровня minor, которые нашёл один агент с уверенностью ниже 80.
3. **Проверка.** Агенты Claude параллельно, по группам файлов, сверяют каждую находку с кодом.
   Ложные снимаются, несущественные и найденные в старом коде уходят в отдельные списки. Ревью
   этим заканчивается: в каталоге прогона лежат `findings.json` и `report.md`.
4. **Спор.** Находки, которые нашли обе стороны, — консенсус, их не оспаривают. Остальное идёт
   другой стороне:
   - раунд 1 — каждая сторона проверяет по коду находки другой и ставит свою severity;
   - раунд 2 — автор отвечает на возражения: соглашается, защищает или уточняет;
   - модератор разбирает оставшиеся споры по коду. Обычно модератор — сама сессия Claude, а по
     просьбе можно запустить двух независимых модераторов на других моделях.
5. **Итог.** У каждого пункта — исход спора и итоговая severity. Видно, какой приоритет был после
   проверки, какой стал и кто его поменял. Подробности — на HTML-странице отчёта с перепиской сторон
   по каждому пункту. Если в сессии есть инструмент Artifact, скил публикует страницу приватно, иначе
   даёт путь к файлу.

Ревью занимает 15–40 минут, спор — ещё 15–30. Всё, что читает пользователь, — по-русски:
замечания, аргументы сторон, вердикты, сводка и отчёт.

После исправлений попросите «повтори обсуждение после правок». Скил начнёт следующий прогон той же
задачи, а агентам покажет находки прошлых прогонов, чтобы они оценили их заново.

Скил не меняет код и историю репозитория: ни коммитов, ни `checkout`, ни `fetch`. Данные прогонов он
пишет в `.cross-review/runs/` того же репозитория и кладёт туда `.gitignore` со строкой `*`, поэтому в
git они не попадают, даже если `.gitignore` репозитория написан белым списком.

## Настройка под репозиторий

Модели, ростер ревьюеров, промты и линзы по умолчанию лежат в плагине, в
[assets/config/](./skills/cross-review/assets/config/). Репозиторий может переопределить их своей папкой
`.cross-review/` в корне. Её коммитит команда, и она действует на каждое перекрёстное ревью этого
репозитория.

| Файл | Что делает |
| --- | --- |
| `cross-review.json` | Частичный конфиг: только ключи, которые меняются. Объекты сливаются с дефолтами по ключам, массивы (`roster`, `lenses`) заменяются целиком |
| `prompts/<имя>.md` | Целиком заменяет одноимённый промт плагина: `review`, `synthesis`, `verify`, `examine`, `respond`, `moderate` |
| `lenses/<имя>.md` | Заменяет линзу плагина или добавляет новую — её можно назвать в своём `roster` |

В `cross-review.json` настраиваются:

- `tiers` — модели уровней. `standard` идёт по умолчанию: Claude `opus:high` против Codex
  `gpt-6.1-sol:high`. `expert` — по словам «эксперт» или «лучшие модели», он в разы дороже. У
  каждого уровня есть и пара независимых модераторов;
- `tier` — уровень, который берётся, когда пользователь не назвал его;
- `roster` — ревьюеры и их линзы. Каждая запись даёт двух агентов, на Claude и на Codex;
- `stages` — включить или выключить синтез и проверку, сколько проверяющих запускать параллельно и
  как делить находки на группы.

Схемы ответов переопределить нельзя: скрипты читают ответы по ним. Неизвестный ключ, промт без
пары в плагине или линза, которой нет ни в одном слое, — ошибка с именем файла и ключа ещё до
запуска, её покажет `show`. Лишний плейсхолдер в промте или линзе всплывает позже — на стадии,
которая этот текст подставляет, а в промтах спора уже после ревью. Поэтому сверяйте свой промт и
линзу с таблицей плейсхолдеров в [references/config.md](./skills/cross-review/references/config.md):
в линзу подставляются те же значения, что и в промт `review`, и буквальный `{{слово}}` в ней —
ошибка.

Пример: репозиторий запускает Codex на модели подешевле и добавляет линзу производительности.

```text
.cross-review/
├── cross-review.json
└── lenses/perf.md
```

```json
{
  "tiers": { "standard": { "codex": "gpt-6-sol:medium" } },
  "roster": [
    { "name": "bugs", "lenses": ["bugs", "impl"] },
    { "name": "perf", "lenses": ["perf", "quality"] }
  ]
}
```

```markdown
---
description: performance regressions on hot paths
---
## Lens: perf

Look for work the change adds to a hot path: a query per item of a loop, a lock held across I/O,
an unbounded cache. Leave micro-optimisations of cold code alone.
```

Начать удобнее с `/cross-review:cross-review-setup` в корне репозитория. Он создаёт:

- `cross-review.json` с одним ключом `tier` — остальное по-прежнему берётся из плагина;
- `README.md` для владельца — что за что отвечает и как переопределить;
- `defaults/` — копию дефолтов плагина: уровни и модели, ростер, все промты и линзы. Скил её не
  читает, это образец.

Чтобы изменить промт или линзу, скопируйте файл из `defaults/` в `prompts/` или `lenses/` и правьте
копию: перекрывает плагин только то, что скопировано. Свои файлы владельца команда не перезаписывает,
а повторный запуск обновляет только `defaults/`, и после обновления плагина `git diff
.cross-review/defaults/` показывает, что в нём изменилось. В конце команда печатает итоговую
конфигурацию: какие агенты пойдут на каких моделях и из какого слоя взят каждый промт и линза. Полная
схема, правила слияния и плейсхолдеры промтов описаны в
[references/config.md](./skills/cross-review/references/config.md).

## Как проверить

Попросите агента в любом git-репозитории: «перекрёстное ревью текущей ветки». Агент должен загрузить
скил `cross-review:cross-review` и сказать одной строкой, какие агенты пойдут на каких моделях.
